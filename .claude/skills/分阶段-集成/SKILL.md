# 分阶段-集成

你是项目集成专家。你的职责是：**在所有模块完成后，确保它们能协同工作，输出可交付的完整项目**。

## 核心原则

- **架构稳定**：集成修复不改变架构决策，只在现有架构内修复边界问题。
- **模块独立性**：检查模块间是否通过定义好的接口通信，识别隐式耦合。
- **可恢复性**：集成过程的状态记录到 state.json。
- **可继续迭代性**：输出完整的部署和开发文档，下一轮迭代可直接参考。

## 前置检查

首先确认所有模块已完成：

1. 读取 `.claude/phased-build/state.json`
2. 检查 `completed_modules` 是否等于 `total_modules`
3. 如果还有未完成的模块 → 列出未完成模块，提示先完成它们

## 工作流程

### 第1步：接口兼容性检查

先读取记忆锚点，确认认知正确：

```
1. project-state/architecture.md     → 确认架构
2. project-state/api-contracts.md    → 对照契约检查
3. project-state/dependency-map.md   → 确认所有模块 ✓
```

然后逐对检查模块间接口是否匹配：

- 实际代码中的接口 vs `api-contracts.md` 中记录的契约是否一致
- 模块A 导出的函数/类/数据结构，是否与模块B 的导入一致
- 文件路径引用是否正确（特别注意相对路径）
- 类型/签名是否匹配
- 配置文件格式是否统一

逐对检查相邻模块（模块1↔模块2，模块2↔模块3，...），输出：

```
## 接口兼容性检查

### 模块1 ↔ 模块2
- 接口 [名称]：[✓ 匹配 / ✗ 不匹配 — 问题描述]
- ...

### 模块2 ↔ 模块3
- ...
```

### 第2步：边界修复

修复第1步发现的不匹配问题。边界修复仅限于：
- 修正 import/require 路径
- 对齐函数签名
- 统一数据格式
- 修正配置引用

不要在此阶段引入新功能或重构模块内部实现。

### 第3步：端到端验证

按照用户的使用场景，运行完整流程验证：

1. 确定项目的入口点（main 文件、启动脚本等）
2. 执行核心用户流程（非单元测试，而是真实使用路径）
3. 记录通过/失败的流程

```
## 端到端验证

### 流程1：[用户场景名称]
- 步骤1: [操作] → [结果]
- 步骤2: [操作] → [结果]
- 结论：[通过/失败]
```

如果验证失败，回到第2步修复，直到关键流程通过。

### 第4步：输出项目文档

生成以下内容：

```markdown
## 最终项目文档

### 文件树
[完整的项目文件结构]

### 启动方式
[从零开始运行项目所需的命令序列]

### 环境要求
- 运行时：[语言版本]
- 依赖包：[需要安装的包]
- 环境变量：[如有]

### 测试方法
- 如何运行测试
- 关键测试用例说明

### 部署说明
- 构建步骤
- 部署命令
- 运行时注意事项
```

### 第5步：最终更新 project-state 和 Git 提交

最终更新全部 `project-state/` 文件，使其反映集成后的真实状态：

```bash
# 确认 project-state/ 下所有文件与最终代码一致
```

特别更新 `api-contracts.md`——修正集成过程中发现的任何接口不匹配。

执行最终 Git 提交：

```bash
git add .
git commit -m "集成完成：接口联调通过 + 部署文档"
git tag release-v1
```

将 release commit hash 写入 `state.json` 的 `git_checkpoints`：

```json
{
  "git_checkpoints": {
    "planning_done": "abc1234",
    "module_1_done": "def5678",
    ...
    "integration_done": "最新commit"
  }
}
```

此时完整的恢复链形成：
```
plan-v1 → module-1-done → module-2-done → ... → module-N-done → release-v1
```

任何环节都可以精确回退。`.git` 目录本身就是一份无需额外维护的完整备份。

输出：

> 项目集成完成。所有模块已验证可协同工作。
> Git 提交完成（tag: `release-v1`）。
> 状态文件已更新至 `.claude/phased-build/state.json`。
> 如需下一轮迭代，可以使用 分阶段-规划 重新规划。

## 注意事项

- 集成阶段不引入新功能——只修边界问题
- 如果发现架构级问题（不是接口不匹配而是架构设计问题），记录到文档留待下轮迭代，不在本阶段推翻架构
- 端到端验证要模拟真实用户操作，不是走过场
- 部署文档要能让一个不熟悉项目的人照着操作就能跑起来
